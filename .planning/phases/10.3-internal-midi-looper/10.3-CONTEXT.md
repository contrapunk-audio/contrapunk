# Phase 10.3: Internal MIDI Looper — Context

**Created:** 2026-08-01
**Status:** Planned in `10.3-01` through `10.3-03`; ready for execution

## Goal

Build and test one reliable internal MIDI phrase looper before continuing Daisy hardware firmware or screenless hardware UX. The looper captures performer events before harmony, then replays them through the current full arrangement so key, scale, harmony, and Companion changes can reharmonize the recorded phrase on later passes.

This phase proves the shared musical and lifecycle behavior in Contrapunk first. It does not build a Daisy looper or audio looper.

## Priority decision

The internal looper is the next product prerequisite. Daisy firmware, Pod/MPK control mapping, and further hardware UX work remain paused until this phase passes automated lifecycle evidence and a desktop performance test.

**Checkpoint completed 2026-08-01:** Pixel Trio was already checkpointed in `a290e226`. Its shared Phrase Context migration, phrase-aware Suspension Garland, cross-surface wiring, generated WASM bindings, scale-preservation fix, and arrangement contracts were reviewed, repaired, tested, and checkpointed separately in `a74e68a7` through `841072a1`. The looper starts from those clean foundations rather than sharing their implementation diff.

## Locked product decisions

1. **MIDI, not audio:** capture NoteOn, NoteOff, velocity, channel, and sustain pedal CC64. Guitar participates through its detected MIDI events; dry guitar audio is not recorded.
2. **One volatile slot:** exactly one loop exists in memory. Reload/restart clears it.
3. **Pre-arrangement capture:** record performer MIDI before harmony and Companion processing.
4. **Reharmonize every pass:** replay uses the current key, scale, arrangement, and role configuration rather than freezing prior generated notes.
5. **Full arrangement with isolated context:** replayed events can drive harmony and Companion roles, but use a loop-owned phrase/runtime context. They must not recursively record themselves, increment or hold open the live Phrase Context, or steal live note ownership.
6. **Pedal-like short-press lifecycle:** `Empty → Armed → Recording → Playing → Stopped → Playing`.
7. **Bar-quantized edges:** first press arms; recording starts on the next downbeat. A second press while recording requests closure; capture ends and playback begins on the next downbeat.
8. **Stopped-transport behavior:** pressing Loop while stopped starts transport, provides one full bar of count-in, then records on the following downbeat.
9. **Long press clears:** Clear ends every active loop-owned note, resets loop sustain, deletes the buffer, and returns to `Empty`.
10. **Single take:** no overdub, undo, merge, or layer editing in this phase.
11. **Boundary safety:** notes still held when recording closes receive matching NoteOff events exactly at the loop boundary. Cross-boundary ties are deferred.
12. **Beat-relative timing:** raw performance offsets are stored in beats without note quantization. Tempo changes stretch/compress playback while preserving musical phase.
13. **Live layering:** live MIDI/guitar-detected notes continue through the live arrangement context while the loop plays through its independent context.
14. **Safe startup:** no persisted loop resumes after application restart.

## State and control contract

The backend exposes explicit actions even when a surface presents them as one button:

- `press`: arm, request close, stop, or resume according to current state;
- `clear`: terminate owned notes and delete the take;
- `status`: state, current/recorded length in beats and bars, and whether closure is pending.

A surface may derive short press and long press from those actions, but timing of a UI gesture must not be implemented inside the looper engine.

## Event and ownership contract

- Add an explicit input origin such as `Live` versus `Loop(slot_id)`; do not infer origin from MIDI channel or target.
- Only `Live` events can be captured.
- Loop replay receives a separate arrangement/Phrase Context runtime while sharing current configuration.
- Every replayed NoteOn and sustain transition has exact loop-owned cleanup on stop, clear, panic, transport stop/reset, seek/loop-back, disable, reconfigure, and failed restore.
- Cleanup uses targeted ownership first; broad All Notes Off is only a defensive fallback.
- A tick window must emit each due event exactly once even when router polling skips over an event offset or crosses the loop boundary.
- Replayed sustain must never leak into live input state.

## First delivery surface

Implement and validate the behavior in the shared Rust core, then expose only the minimum Tauri desktop controls needed for manual performance testing. Other surfaces must capability-gate the looper until they implement the same contract.

The phase does not claim WASM, plugin, or Daisy parity. Those are follow-up phases after desktop acceptance.

## Required automated evidence

1. A stopped transport starts, counts in one bar, and enters Recording on the expected downbeat.
2. A running transport arms and starts at the next downbeat without shifting phase.
3. The closing press captures through the next downbeat, synthesizes boundary NoteOffs, and begins seamless playback.
4. NoteOn/NoteOff velocity/channel timing and CC64 sustain round-trip at beat-relative offsets.
5. Every due event fires exactly once across coarse, fine, delayed, and boundary-crossing tick windows.
6. Changing tempo preserves beat phase with no accumulated drift.
7. Changing key or arrangement changes generated replay output without mutating the recorded source buffer.
8. Loop replay exercises the full arrangement while leaving live Phrase Context and capture state unchanged.
9. Live performance and replay coexist without recursive capture or ownership collision.
10. Stop, clear, panic, transport stop/reset, backward seek, disable, and reconfigure end with zero active loop-owned notes, zero pending events, and sustain up.
11. Empty takes and malformed/unmatched input releases fail safely.
12. Serialization/persistence is absent by design; restart begins Empty.

## Manual acceptance

After automated checks pass, run one desktop performance session:

1. Start with transport stopped and record a short MPK phrase after the one-bar count-in.
2. Close on a later downbeat and verify seamless replay.
3. Play live notes over it.
4. Change key and arrangement and confirm the source phrase is reharmonized.
5. Repeat using clean monophonic guitar detection.
6. Exercise stop/resume and long-clear while notes or sustain are active.
7. Confirm no stuck notes, duplicate attacks, phrase-state contamination, or timing drift.

Daisy hardware planning remains blocked until the user accepts this session.

## Explicit non-goals

- Audio recording or dry-guitar capture
- Multiple loop slots
- Overdub, undo, replace-in-place, or loop editing
- Post-harmony/output capture or frozen playback
- Note quantization, swing correction, or time stretching independent of transport tempo
- Pitch bend, aftertouch, arbitrary CC capture, SysEx, or MIDI file import/export
- Cross-boundary tied notes
- Loop persistence or rig serialization
- Ableton Link
- WASM, plugin, or Daisy firmware parity
- Hardware control mapping or enclosure UX
