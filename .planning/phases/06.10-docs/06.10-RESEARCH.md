# Phase 6.10: Docs - Research

**Researched:** 2026-02-05
**Domain:** Rust documentation, rustdoc, developer documentation, project documentation
**Confidence:** HIGH

## Summary

This phase focuses on additional documentation work following the Phase 6.9 README rewrite. The current documentation state is: README.md covers basic installation and usage, module-level docs (`//!`) exist for core modules, but many public items lack doc comments, there's no CONTRIBUTING.md, no CHANGELOG.md, and no generated rustdoc hosted anywhere.

Research identified three primary documentation areas for improvement:

1. **Rustdoc coverage** - Add doc comments (`///`) to all public APIs with examples, making the crate documentation complete and useful for developers who want to extend or understand the code.

2. **Developer guides** - Create CONTRIBUTING.md with build instructions, architecture overview, and contribution guidelines.

3. **API documentation hosting** - Configure GitHub Pages or similar to host generated rustdoc, making API documentation accessible without cloning the repo.

**Primary recommendation:** Focus on improving rustdoc coverage for public APIs (harmony engine, scale system, chord detection) since these are the most valuable for developers, then add CONTRIBUTING.md for contributor onboarding.

### Pattern 1: Module-Level Documentation

**What:** Every module should have `//!` at the top explaining its purpose and main types.

**When to use:** Every `.rs` file that is part of the public API.

**Example:**
```rust
// Source: https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html
//! Harmony engine for MIDI note transformation.
//!
//! This module provides the core harmony generation functionality,
//! including scale-aware transposition and multiple harmony modes.
//!
//! # Main Types
//!
//! - [`HarmonyEngine`] - The main entry point for harmonizing notes
//! - [`Scale`] - Musical scale with diatonic transposition
//! - [`HarmonyMode`] - Available harmony algorithms (8 modes)
//!
//! # Example
//!
//! ```ignore
//! use contrapunk::harmony::{HarmonyEngine, Key, HarmonyMode, ScaleMode};
//!
//! let engine = HarmonyEngine::new(Key::C, ScaleMode::Ionian);
//! // Harmonize notes through the engine...
//! ```
```

### Pattern 2: Public Item Documentation

**What:** Every public struct, enum, function, trait, and method should have `///` documentation.

**When to use:** All `pub` items.

**Example:**
```rust
// Source: https://rust-lang.github.io/api-guidelines/documentation.html
/// Musical keys (C through B, 12 options).
///
/// Represents the tonic of a scale. Used with [`ScaleMode`] to define
/// the complete scale for harmony generation.
///
/// # Example
///
/// ```
/// use contrapunk::harmony::Key;
///
/// let key = Key::C;
/// assert_eq!(key.semitones_from_c(), 0);
///
/// let key = Key::G;
/// assert_eq!(key.semitones_from_c(), 7);
/// ```
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Key {
    C, Db, D, Eb, E, F, Gb, G, Ab, A, Bb, B,
}
```

### Pattern 3: Special Sections

**What:** Use standard sections for specific documentation needs.

**When to use:** Based on function/method behavior.

**Sections:**
- `# Errors` - When the function can return an error
- `# Panics` - When the function can panic
- `# Safety` - For unsafe functions (not applicable to this project)
- `# Examples` - Always include for public items

**Example:**
```rust
/// Transposes a note by N scale degrees (diatonic transposition).
///
/// Unlike chromatic transposition (fixed semitones), this moves
/// by scale degrees, so the interval size varies based on position
/// in the scale.
///
/// # Arguments
///
/// * `note` - The MIDI note to transpose
/// * `degrees` - Number of scale degrees to move (positive = up, negative = down)
///
/// # Returns
///
/// The transposed note, or `None` if the result would be out of MIDI range (0-127)
/// or if the input note is not in the scale.
///
/// # Examples
///
/// ```
/// use contrapunk::harmony::Scale;
/// use wmidi::Note;
///
/// let scale = Scale::major(0);  // C major
/// let result = scale.transpose_diatonic(Note::C4, 2);
/// assert_eq!(result, Some(Note::E4));  // C + 2 degrees = E (major third)
/// ```
pub fn transpose_diatonic(&self, note: Note, degrees: i8) -> Option<Note>
```

### Anti-Patterns to Avoid

- **Copy-paste documentation:** Don't just repeat the function signature in prose
- **Missing examples:** Every public item should have at least one example
- **Undocumented panics:** If code can panic, document it in a `# Panics` section
- **Orphan types:** Types referenced in docs should be linked with backticks

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| API documentation | Hand-written markdown | rustdoc (`cargo doc`) | Automatically syncs with code, includes type links |
| Hosting docs | Custom web server | GitHub Pages | Free, automatic deployment possible via Actions |
| Code examples | Untested snippets | Doctests (`/// `) | Examples are compiled and tested by `cargo test` |

**Key insight:** Rust's documentation tooling is excellent. Writing doc comments with examples gives you both documentation AND tests. Don't maintain separate documentation files for API reference.

## Common Pitfalls

### Pitfall 1: Untested Examples

**What goes wrong:** Documentation examples become stale as code changes
**Why it happens:** Examples written without being tested
**How to avoid:** Use `///` doctests that compile with `cargo test --doc`. Use `ignore` attribute sparingly.
**Warning signs:** Examples that don't compile or produce wrong output

### Pitfall 2: Missing Links

**What goes wrong:** Types mentioned in docs aren't clickable in rustdoc
**Why it happens:** Forgetting to use backtick syntax for type references
**How to avoid:** Reference types with backticks: [`HarmonyEngine`], [`Scale`]
**Warning signs:** Plain text type names without brackets

### Pitfall 3: Feature-Gated Documentation

**What goes wrong:** `cargo doc` fails because it doesn't enable features
**Why it happens:** Items behind feature flags aren't documented by default
**How to avoid:** Run `cargo doc --all-features` or document conditional compilation
**Warning signs:** Missing items in generated docs, broken links to gated types

### Pitfall 4: Overly Technical Language

**What goes wrong:** Documentation is hard to understand for newcomers
**Why it happens:** Writing for yourself instead of readers
**How to avoid:** Explain concepts, provide context, show use cases
**Warning signs:** No examples, jargon-heavy prose, assuming prior knowledge

//!

//! - **[`HarmonyEngine`]** - Orchestrates note processing through the selected mode
//!
//! # Harmony Modes
//!
//! | Mode | Description |
//! |------|-------------|
//! | PassThrough | No harmony, notes pass through unchanged |
//! | DiatonicThirds | Add diatonic third above each note |
//! | DiatonicFourths | Add diatonic fourth above each note |
//! | RandomBelow | Add random diatonic interval below |
//! | RandomBelowNoSeconds | Random below, excluding seconds |
//! | ContraryMotion | Harmony moves opposite to melody direction |
//! | StrictCounterpoint | Traditional voice leading rules |
//! | BarryHarris | Barry Harris 6th diminished movement |
//!
//! # Scale Modes
//!
//! 28 scale modes organized into 5 families:
//! - Church modes (7): Ionian, Dorian, Phrygian, Lydian, Mixolydian, Aeolian, Locrian
//! - Harmonic minor modes (7)
//! - Melodic minor modes (7)
//! - Exotic scales (5): Double Harmonic, Hungarian Minor, etc.
//! - Barry Harris 6th Diminished (2): Major and Minor variants
```

### CONTRIBUTING.md Template

```markdown
# Contributing to Contrapunk

## Development Setup

### Prerequisites

- Rust stable (rustup recommended)
- For native: ALSA dev libs on Linux (`sudo apt-get install libasound2-dev`)
- For WASM: `cargo install trunk`

### Building

```bash
# Native debug build
cargo build

# Native release build
cargo build --release

# WASM build
trunk build

# WASM dev server (http://localhost:8080)
trunk serve
```

### Testing

```bash
cargo test           # All tests
cargo test --doc     # Documentation tests only
```

### Linting

```bash
cargo clippy
cargo fmt -- --check
```

## Architecture Overview

Key modules:

- `harmony/` - Music theory engine (scales, modes, chord detection)
- `humanize/` - Timing variation (jitter, groove, beat clock)
- `midi/` - MIDI I/O (native via midir, WASM via Web MIDI API)
- `app.rs` - Main application state and eframe integration
- `ui.rs` - GUI layout and rendering

## Making Changes

1. Fork the repository
2. Create a feature branch (`git checkout -b feature/your-feature`)
3. Make changes with tests
4. Run `cargo test` and `cargo clippy`
5. Submit a pull request

## Code Style

- Follow Rust conventions (rustfmt)
- Add doc comments to public items
- Include examples in doc comments where practical
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| README-only docs | README + rustdoc + CONTRIBUTING | Rust ecosystem maturity | Better developer experience |
| Hand-written API docs | Auto-generated from code comments | rustdoc since Rust 1.0 | Always up-to-date |

**Deprecated/outdated:**
- Wiki pages for API docs: rustdoc is better because it's always in sync with code
- Separate example files without doctests: hard to maintain, often broken
