<task type="auto">
  <name>Task 2: Refactor router for GUI integration with shared state</name>
  <files>src/router.rs, src/app.rs, src/main.rs</files>
  <action>
Refactor the router to work with shared state and be spawnable from GUI:

1. In src/router.rs, create a new function for GUI mode:
   ```rust
   use std::sync::{Arc, Mutex};

   pub struct GUIRouterState {
       pub input_notes: HashSet<u8>,
       pub harmony_notes: HashSet<u8>,
       pub stop_signal: bool,
   }

   pub fn spawn_gui_router(
       input_port: usize,
       output_ports: Vec<usize>,
       key: Key,
       mode: HarmonyMode,
       state: Arc<Mutex<GUIRouterState>>,
       ctx: egui::Context,
   ) -> Result<JoinHandle<Result<()>>>
   ```

2. The spawned thread should:
   - Create HarmonyEngine with provided key/mode
   - Connect to MIDI ports
   - Loop processing messages (like run_router but non-blocking)
   - On Note-On: update state.input_notes and state.harmony_notes, call ctx.request_repaint()
   - On Note-Off: remove from input_notes and harmony_notes, call ctx.request_repaint()
   - Check state.stop_signal each iteration to allow clean shutdown
   - Read key/mode from a shared config (or accept changes via channel)

3. For simplicity in this plan, the router thread receives initial key/mode. Dynamic changes will be addressed by stopping and restarting the router with new config.

4. In src/app.rs:
   - Add gui_state: Option<Arc<Mutex<GUIRouterState>>> field to ContrapunkApp
   - Add router_handle: Option<JoinHandle<...>> field
   - On Start click: spawn_gui_router, store handle
   - On Stop click: set stop_signal = true, join the handle, clear gui_state

5. Keep the existing run_router() for CLI mode unchanged.

6. In src/main.rs, the GUI path should NOT call run_router - it uses the GUI's start button instead.
  </action>
  <verify>cargo check --features gui</verify>
  <done>Router can be spawned from GUI Start button and stopped via Stop button</done>
</task>
