# Phase 06.2: Voice Leading - Research

**Researched:** 2026-01-30
**Domain:** Algorithmic counterpoint / voice leading in real-time MIDI
**Confidence:** MEDIUM (music theory is well-established; real-time implementation patterns are less documented)

## Summary

Voice leading is the art of moving individual voices smoothly when chords change. The existing `CounterpointState` in `src/harmony/stateful.rs` already implements basic two-voice counterpoint (parallel fifth avoidance, stepwise motion preference, interval variety tracking). Phase 06.2 needs to evolve this into a proper multi-voice system with SATB register management, common-tone retention, dissonance handling (suspensions/resolutions), and selectable style presets.

The core challenge is that voice leading is inherently a **constraint satisfaction problem** over multiple simultaneous voices, but the current architecture processes voices as independent chained pairs. The key architectural decision is whether to keep the chained-pair model (simpler, fits existing architecture) or move to a chord-aware voicing system (more correct, significant refactor).

**Primary recommendation:** Extend the existing `CounterpointState` into a `VoiceLeadingEngine` that operates as a post-processor on harmony output, re-voicing chord tones to minimize total voice movement while respecting counterpoint rules. Keep it as a separate processing stage that wraps `HarmonyEngine` output rather than replacing individual mode logic.

### Pattern 1: Post-Processor Architecture
**What:** Voice leading operates AFTER harmony generation, re-voicing the output.
**When to use:** Always. This keeps harmony modes independent from voice leading.
**Example:**
```rust
/// Voice leading as a post-processing step on harmony output.
///
/// Input: Vec<Note> from HarmonyEngine::harmonize()
///        [melody, harmony1, harmony2, harmony3]
/// Output: Vec<Note> with voices re-arranged for smooth leading
///         [melody, re-voiced_h1, re-voiced_h2, re-voiced_h3]
pub struct VoiceLeadingProcessor {
    /// Previous chord voicing (for calculating minimal movement)
    previous_voicing: Option<Vec<Note>>,
    /// Style rules to apply
    style: VoiceLeadingStyle,
    /// Whether voice leading is enabled
    enabled: bool,
    /// Per-voice register constraints (SATB ranges)
    voice_registers: Vec<VoiceRegister>,
    /// Pending suspensions/resolutions
    suspension_state: SuspensionState,
}

impl VoiceLeadingProcessor {
    /// Re-voice a chord for smooth voice leading.
    /// Melody (index 0) is NEVER modified.
    pub fn process(&mut self, notes: &mut Vec<Note>, scale: &Scale) {
        if !self.enabled || notes.len() <= 1 {
            return;
        }
        // 1. Identify chord tones (harmony notes, indices 1..n)
        // 2. For each voice, find closest octave placement to previous note
        // 3. Check constraints (no parallel 5ths/8ves, no voice crossing)
        // 4. Apply suspension/resolution if style requires it
        // 5. Update previous_voicing
    }
}
```

### Pattern 2: Nearest-Voicing Algorithm (Core of Voice Leading)
**What:** When a chord changes, each voice moves to the nearest available chord tone.
**When to use:** This is THE fundamental algorithm for smooth voice leading.
**Example:**
```rust
/// Find the nearest octave placement of `target_pitch_class` to `current_note`.
/// This is how voices move by smallest interval.
fn nearest_voicing(current_note: Note, target_pitch_class: u8) -> Note {
    let current_midi = u8::from(current_note);
    let current_pc = current_midi % 12;
    let target_pc = target_pitch_class % 12;

    // Calculate semitone distances (up and down)
    let up = (target_pc as i8 - current_pc as i8 + 12) % 12;
    let down = (current_pc as i8 - target_pc as i8 + 12) % 12;

    let new_midi = if up <= down {
        current_midi.saturating_add(up as u8)
    } else {
        current_midi.saturating_sub(down as u8)
    };

    Note::try_from(new_midi.clamp(0, 127)).unwrap_or(current_note)
}
```

### Pattern 3: Constraint Checker (Separate from Voicing)
**What:** Rules checking is a separate pass from voice assignment.
**When to use:** After tentative voicing, validate and adjust.
```rust
/// Check voice leading between two chords.
/// Returns a list of violations.
fn check_voice_leading(
    prev: &[Note],     // previous chord voicing
    current: &[Note],  // proposed new voicing
) -> Vec<VoiceLedViolation> {
    let mut violations = vec![];

    for i in 0..prev.len().min(current.len()) {
        for j in (i+1)..prev.len().min(current.len()) {
            // Check parallel fifths
            let prev_interval = interval_class(prev[i], prev[j]);
            let curr_interval = interval_class(current[i], current[j]);
            if prev_interval == 7 && curr_interval == 7 {
                violations.push(VoiceLedViolation::ParallelFifths(i, j));

            // Check parallel octaves
            if prev_interval == 0 && curr_interval == 0 &&

            }
        }
    }
    violations
}
```

### Pattern 4: Style Presets as Rule Weight Tables
**What:** Different counterpoint styles are just different weights on the same rules.
**When to use:** For the style selector (Palestrina, Bach, Jazz, Free).
```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum VoiceLeadingStyle {
    Palestrina,    // Strictest: no parallel 5ths/8ves, stepwise only, prepared dissonance
    BachChorale,   // Strict: SATB ranges enforced, common tones held, some leaps OK
    Jazz,          // Relaxed: parallel motion OK, chromatic approach, drop voicings
    Free,          // Minimal: just avoid voice crossing, prefer smooth motion
}

pub struct StyleRules {
    pub parallel_fifths_penalty: i32,    // -100 for strict, 0 for jazz
    pub parallel_octaves_penalty: i32,
    pub voice_crossing_penalty: i32,     // -100 for strict, -20 for free
    pub stepwise_bonus: i32,             // +10 for Palestrina, +4 for jazz
    pub common_tone_bonus: i32,          // +8 for Bach, +2 for free
    pub leap_penalty_per_semitone: i32,  // -1 per semitone for strict, 0 for jazz
    pub max_leap_semitones: u8,          // 7 for Palestrina, 12 for jazz, 127 for free
    pub require_suspension_prep: bool,   // true for Palestrina, false otherwise
    pub allow_chromatic_approach: bool,  // false for Palestrina, true for jazz
}
```

### Anti-Patterns to Avoid
- **Processing voices independently without chord context:** The existing chained-pair model (harm2 derived from harm1) produces independent voice leading that can create parallel 5ths between non-adjacent voices. Voice leading MUST consider all voices simultaneously.
- **Modifying the melody note:** Index 0 is ALWAYS the player's input. Voice leading only adjusts harmony voices (indices 1+).
- **Allocating per-note:** Voice leading runs on every MIDI note. Use pre-allocated buffers, not fresh Vec allocations per call. Keep candidate arrays on the stack.
- **Blocking on search:** Never use exhaustive search over all possible voicings. With 4 voices and 10 octaves each, that is 10^4 = 10,000 combinations. Use greedy nearest-voicing with constraint repair instead.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Interval classification | Manual semitone math everywhere | Centralized `interval_class(a, b) -> u8` function (already exists in CounterpointState) | Error-prone, inconsistent if duplicated |
| SATB ranges | Magic numbers scattered | `VoiceRegister` enum with `range() -> (u8, u8)` method | Standard ranges: S(60-81), A(55-76), T(48-69), B(40-64) |
| Parallel detection | Ad-hoc checks per mode | Shared `check_parallels(prev, curr) -> Vec<Violation>` | Same logic needed across all styles |
| Common tone detection | Custom comparison | `find_common_tones(prev_chord: &[u8], new_chord: &[u8]) -> Vec<u8>` | Pitch class comparison, not MIDI note equality |

**Key insight:** The existing `CounterpointState` already has `interval_class()`, `is_perfect_interval()`, and the scoring framework. Extract and generalize these into shared utilities rather than duplicating them.

## Common Pitfalls

### Pitfall 1: Voice Crossing Creates Timbre Confusion
**What goes wrong:** When alto goes above soprano, the perceived voices swap, creating confusion even if individual lines are smooth.
**Why it happens:** Nearest-voicing algorithm can cross voices when chord tones are close together.
**How to avoid:** After nearest-voicing, check that voice ordering is maintained (soprano > alto > tenor > bass in MIDI number). If crossed, swap the assignments.
**Warning signs:** Two output ports producing notes that frequently swap relative position.

### Pitfall 2: Parallel Fifths Between Non-Adjacent Voices
**What goes wrong:** Soprano-tenor or soprano-bass move in parallel fifths while alto masks it. Still sounds bad.
**Why it happens:** Only checking adjacent voice pairs, or only checking melody-harmony pairs as the current code does.
**How to avoid:** Check ALL voice pairs (n*(n-1)/2 pairs for n voices). For 4 voices that is 6 pairs.
**Warning signs:** Tests only check adjacent pairs.

### Pitfall 3: Common Tone Not Held Creates Unnecessary Movement
**What goes wrong:** When moving from C major to A minor (sharing C and E), all voices move instead of holding the common tones.
**Why it happens:** Nearest-voicing algorithm treats each voice independently without checking if the target pitch is already present.
**How to avoid:** First pass: identify common tones between old and new chord. Assign those voices to hold. Second pass: move remaining voices to remaining chord tones.
**Warning signs:** Excessive voice movement on closely related chords (I-vi, I-IV, etc.).

### Pitfall 4: Suspension Without Resolution Creates Hanging Dissonance
**What goes wrong:** A voice is suspended (held from previous chord) creating a dissonance, but the next chord change happens before resolution.
**Why it happens:** Suspensions need 3 states: preparation (consonant) -> suspension (dissonant, held over) -> resolution (step down). If the player changes chords too fast, step 3 never happens.
**How to avoid:** Track suspension state. If a new chord arrives before resolution, force-resolve immediately (snap to nearest consonance). Make suspension duration configurable.
**Warning signs:** Dissonant notes stuck ringing indefinitely.

### Pitfall 5: Real-Time Latency from Over-Engineering
**What goes wrong:** Complex constraint satisfaction or backtracking search takes >5ms per note.
**Why it happens:** Trying to find the globally optimal voicing rather than a good-enough one.
**How to avoid:** Use greedy nearest-voicing + repair, not exhaustive search. Profile with `cargo bench`. The current scoring approach in `CounterpointState` (score candidates, pick best) is the right paradigm -- just extend it to multi-voice.
**Warning signs:** Audible latency or dropped notes during fast passages.

### Pitfall 6: State Accumulation on Style/Key Change
**What goes wrong:** Switching styles mid-performance carries stale `previous_voicing` state that conflicts with new rules.
**Why it happens:** Not resetting voice leading state on configuration change.
**How to avoid:** Reset `previous_voicing` and `suspension_state` whenever style, key, or mode changes (follow existing pattern in `HarmonyEngine::set_key()`).
**Warning signs:** First chord after a change sounds wrong, then it recovers.

## Code Examples

### Common Tone Retention
```rust
/// Identify pitch classes common to both chords.
/// Returns indices in `new_pcs` that match any pitch class in `prev_notes`.
fn find_common_tones(prev_notes: &[Note], new_pcs: &[u8]) -> Vec<(usize, u8)> {
    // prev pitch classes
    let prev_pcs: Vec<u8> = prev_notes.iter().map(|n| u8::from(*n) % 12).collect();
    new_pcs.iter().enumerate()
        .filter(|(_, pc)| prev_pcs.contains(pc))
        .map(|(i, pc)| (i, *pc))
        .collect()
}
```

### SATB Register Constraints
```rust
#[derive(Clone, Copy, Debug)]
pub enum VoiceRegister {
    Soprano,  // C4 (60) to A5 (81)
    Alto,     // G3 (55) to E5 (76)
    Tenor,    // C3 (48) to A4 (69)
    Bass,     // E2 (40) to E4 (64)
}

impl VoiceRegister {
    pub fn range(&self) -> (u8, u8) {
        match self {
            VoiceRegister::Soprano => (60, 81),
            VoiceRegister::Alto    => (55, 76),
            VoiceRegister::Tenor   => (48, 69),
            VoiceRegister::Bass    => (40, 64),
        }
    }

    pub fn contains(&self, note: Note) -> bool {
        let midi = u8::from(note);
        let (lo, hi) = self.range();
        midi >= lo && midi <= hi
    }

    /// Clamp a note to this register (find nearest octave placement within range).
    pub fn clamp(&self, note: Note) -> Note {
        let midi = u8::from(note);
        let (lo, hi) = self.range();
        let pc = midi % 12;

        // Find all octave placements of this pitch class within range
        let mut best = midi.clamp(lo, hi);
        let mut best_dist = 127u8;

        for octave_start in (0..=120).step_by(12) {
            let candidate = octave_start + pc;
            if candidate >= lo && candidate <= hi {
                let dist = (candidate as i8 - midi as i8).unsigned_abs();
                if dist < best_dist {
                    best = candidate;
                    best_dist = dist;
                }
            }
        }

        Note::try_from(best).unwrap_or(note)
    }
}
```

### Voice Leading Scoring (Multi-Voice Extension of Existing Pattern)
```rust
/// Score a complete voicing candidate.
/// Lower total voice movement = higher score.
fn score_voicing(
    prev: &[Note],
    candidate: &[Note],
    style: &StyleRules,
) -> i32 {
    let mut score: i32 = 0;

    // Voice movement cost (skip index 0 = melody, already fixed)
    for i in 1..prev.len().min(candidate.len()) {
        let prev_midi = u8::from(prev[i]) as i32;
        let curr_midi = u8::from(candidate[i]) as i32;
        let movement = (curr_midi - prev_midi).abs();

        if movement == 0 {
            score += style.common_tone_bonus; // Holding common tone
        } else if movement <= 2 {
            score += style.stepwise_bonus; // Stepwise motion
        } else {
            score -= movement * style.leap_penalty_per_semitone;
        }
    }

    // Parallel motion penalties (check ALL pairs)
    for i in 0..candidate.len() {
        for j in (i+1)..candidate.len() {
            if i < prev.len() && j < prev.len() {
                let prev_int = interval_class_u8(prev[i], prev[j]);
                let curr_int = interval_class_u8(candidate[i], candidate[j]);
                if prev_int == 7 && curr_int == 7 {
                    score += style.parallel_fifths_penalty;
                }
                if prev_int == 0 && curr_int == 0 {
                    score += style.parallel_octaves_penalty;
                }
            }
        }
    }

    score
}

fn interval_class_u8(a: Note, b: Note) -> u8 {
    let a_midi = u8::from(a);
    let b_midi = u8::from(b);
    (a_midi.abs_diff(b_midi)) % 12
}
```

**What Phase 06.2 adds:**
- Multi-voice simultaneous evaluation (all pairs checked)
- SATB register assignment and enforcement

- Style presets as weight tables
- Post-processor architecture (works with ALL harmony modes)
- GUI toggle

## Open Questions

1. **Chord detection from harmony output:**
   - What we know: HarmonyEngine outputs individual notes via chained pairs. Voice leading needs to know the "chord" to find common tones.
   - What's unclear: Should voice leading infer the chord from the output notes, or should HarmonyEngine provide chord context?
   - Recommendation: Treat the output note set as the chord. No chord detection needed -- just re-voice the given pitch classes for smooth motion.

2. **Suspension timing in note-at-a-time model:**
   - What we know: The engine processes one melody note at a time (Note-On triggers harmonize).
   - What's unclear: Suspensions need temporal awareness (hold note X until next note, then resolve). With single-note processing, there is no "wait" concept.
   - Recommendation: Implement suspensions as a state machine: on chord change, delay one voice's movement to the NEXT chord change. This gives a one-chord-length suspension without needing timing.

3. **Interaction with OctaveMode:**
   - What we know: OctaveMode (Spread, Mirror, etc.) modifies note octaves after harmony.
   - What's unclear: Should voice leading run before or after octave mode?
   - Recommendation: Voice leading runs BEFORE octave mode. VL produces smooth voicings; then octave mode can spread/mirror the result. This preserves both features' intent.
