# Phase 6.1: Humanization UI Fix - Research

**Researched:** 2026-01-29
**Domain:** egui WASM rendering, WASM MIDI humanization integration
**Confidence:** HIGH

## Summary

This phase addresses three issues: (1) humanization controls may not be visible in the browser/WASM build, (2) humanization audio effects do not work in WASM (code exists only in native router), and (3) UI controls need redesign for clarity.

Code inspection reveals the root causes clearly. The humanization UI controls (app.rs lines 669-720) are inside a `ScrollArea` in a `SidePanel` with `default_width(220.0)`. The controls ARE rendered for WASM (no `#[cfg]` gate). The visibility issue is likely a viewport/scroll problem on smaller browser windows. The audio effects issue is definitive: WASM note handling (`handle_wasm_note_on` / `handle_wasm_note_off`, lines 420-472) sends notes directly to Web MIDI outputs WITHOUT passing through the `Humanizer` engine. The native router (router.rs) integrates humanization fully, but the WASM path bypasses it entirely.

**Primary recommendation:** Integrate the `Humanizer` engine into the WASM MIDI processing path (`process_wasm_midi`), fix UI layout for browser viewports, and add collapsible sections for better UX.

## Architecture Patterns

### Pattern 1: WASM Humanizer Integration
**What:** Add `Humanizer` and `DelayQueue` fields to `ContrapunkApp` (WASM-only fields), process notes through humanizer in `handle_wasm_note_on`/`handle_wasm_note_off`, drain delay queue each frame in `update()`.
**When to use:** This is the core fix for HUM-UI-02 (effects don't work in WASM).
**Example:**
```rust
// In ContrapunkApp struct (wasm32 fields):
#[cfg(target_arch = "wasm32")]
wasm_humanizer: Humanizer,
#[cfg(target_arch = "wasm32")]
wasm_delay_queue: DelayQueue,

// In handle_wasm_note_on, after harmonize:
for (i, &n) in notes.iter().enumerate() {
    if i == 0 {
        // Melody: pass through unchanged
        send_wasm_note_on(access, &output_ids[port], channel, n, velocity);
    } else {
        // Harmony: humanize
        let hn = self.wasm_humanizer.humanize_note_on(n, channel, velocity, port);
        if hn.delay_ms == 0 {
            send_wasm_note_on(access, &output_ids[hn.port], hn.channel, hn.note, hn.velocity);
        } else {
            self.wasm_delay_queue.push(hn, now_ms);
        }
    }
}

// In update(), drain delay queue each frame:
let now = web_sys_now_ms();
while let Some(hn) = self.wasm_delay_queue.pop_ready(now) {
    // send hn to web midi output
}
```

### Pattern 2: Collapsible UI Sections
**What:** Replace flat vertical layout with `CollapsingHeader` for each humanization sub-section (Beat Clock, Jitter, Velocity, Duration, Swing). This reduces vertical space and makes controls discoverable.
**When to use:** For HUM-UI-03 (UI redesign).
**Example:**
```rust
egui::CollapsingHeader::new("Timing Jitter")
    .default_open(false)
    .show(ui, |ui| {
        ui.checkbox(&mut config.jitter_enabled, "Enable");
        if config.jitter_enabled {
            ui.add(egui::Slider::new(&mut config.jitter_min_ms, 0..=50).text("Min ms"));
            ui.add(egui::Slider::new(&mut config.jitter_max_ms, 0..=50).text("Max ms"));
        }
    });
```

### Pattern 3: SidePanel Min Height / Auto-Scroll
**What:** Ensure the SidePanel ScrollArea has `auto_shrink(false)` and the panel has sufficient min width for sliders. On small viewports, the ScrollArea handles overflow.
**When to use:** For HUM-UI-01 (visibility fix).

### Anti-Patterns to Avoid
- **Duplicating humanizer logic in WASM path:** Reuse the existing `Humanizer` struct, do not rewrite the math.
- **Using `Instant` in WASM code:** Use `f64` milliseconds everywhere (already the project convention per BeatClock).
- **Blocking the UI thread with setTimeout polling:** Use frame-based drain in `update()` instead.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Humanization math | New WASM-specific humanization | Existing `Humanizer` struct | Already correct, tested in native path |
| Delay queue | New WASM delay queue | Existing `DelayQueue` from `src/humanize/scheduler.rs` | Already uses f64 ms timestamps, WASM-compatible by design |
| Collapsible sections | Manual show/hide state | `egui::CollapsingHeader` | Built into egui, handles animation and state |

**Key insight:** The Humanizer and DelayQueue are already WASM-compatible (f64 ms, no Instant). The only missing piece is wiring them into the WASM MIDI processing path.

## Common Pitfalls

### Pitfall 1: Forgetting to Sync HumanizeConfig in WASM
**What goes wrong:** User changes humanization sliders but WASM humanizer keeps using old config.
**Why it happens:** Native path syncs config via `router_state` mutex (app.rs line 723-731, gated by `#[cfg(not(target_arch = "wasm32"))]`). WASM has no equivalent sync.
**How to avoid:** In the WASM update loop, sync `self.humanize_config` to `self.wasm_humanizer.update_config()` each frame.
**Warning signs:** Slider changes have no effect on WASM output.

### Pitfall 2: DelayQueue Drain Missing in WASM
**What goes wrong:** Delayed notes never send because nobody drains the queue.
**Why it happens:** Native router has its own loop that drains. WASM needs drain in `update()`.
**How to avoid:** Add drain loop in `update()` method, before or after MIDI processing.
**Warning signs:** Notes with jitter or swing never sound.

### Pitfall 3: ScrollArea Content Clipped on Small Viewports
**What goes wrong:** Humanization section falls below the visible area in browser.
**Why it happens:** SidePanel has fixed 220px width; content above humanization (key, mode, octave, ports, start/stop) takes significant vertical space. On typical browser viewports (768px height minus browser chrome), humanization may be below fold.
**How to avoid:** Use `CollapsingHeader` to reduce default height. Ensure ScrollArea scrollbar is visible. Consider moving humanization to a separate tab or bottom section if space is critical.
**Warning signs:** Controls appear on desktop native but not in browser at default zoom.

### Pitfall 4: Metronome Click in WASM
**What goes wrong:** Metronome sends MIDI notes on channel 10, but the WASM path does not have metronome integration.
**Why it happens:** Metronome is wired into native router only.
**How to avoid:** Add metronome beat-crossing check in WASM update loop, same as native router does.
**Warning signs:** Metronome checkbox has no effect in browser.

        // Send hn via web::send_to_output
    }

## Open Questions

1. **Is the visibility issue purely viewport-related or is there an egui WASM ScrollArea bug?**
   - What we know: Code has no cfg gate; ScrollArea is used. The site is at contrapunk.fly.dev.
   - What's unclear: Whether the issue is just scroll position or something deeper.
   - Recommendation: First fix is to add CollapsingHeaders and test. If still invisible, investigate egui 0.33 WASM ScrollArea behavior specifically.

2. **Should metronome use Web Audio API instead of MIDI channel 10 in WASM?**
   - What we know: MIDI channel 10 requires an external synth to be connected. Browser users may not have one.
   - What's unclear: Whether Web Audio click is in scope.
   - Recommendation: Keep MIDI channel 10 for consistency. Web Audio metronome is a future enhancement.
