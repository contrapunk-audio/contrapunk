**src/main.rs:**
Add clap-based argument parsing. Define a struct with derive:
```
#[derive(clap::Parser)]
struct Args {
    #[arg(long)]
    server: bool,
    #[arg(long)]
    client: Option<String>,  // host:port
    #[arg(long, default_value_t = 9900)]
    port: u16,
}
```

Update main() to parse args first. Routing logic:
- If args.server: call server::run_server with ServerConfig { port: args.port, ..Default::default() }
- If args.client is Some(addr): call a new `run_client(addr)` function (implemented in Task 2)
- Otherwise: existing GUI or CLI logic (unchanged)

The clap parsing must work for both GUI and non-GUI builds. Use `#[cfg]` gates carefully - the Args struct and server/client branches are unconditional. The existing GUI/CLI fallback remains gated as before.

Important: The existing CLI mode (non-GUI, no flags) must still work when no args are passed. clap's default behavior with no required args handles this.

<task type="auto">
  <name>Task 2: Implement client mode</name>
  <files>src/main.rs</files>
  <action>
Add a `run_client(addr: &str) -> Result<()>` function (can be in main.rs or a new src/client.rs - prefer main.rs to keep it simple since it's ~80 lines):

1. Connect TcpStream to addr. Set nodelay(true), read_timeout(30s), write_timeout(5s).
2. Print "Connected to Contrapunk server at {addr}"
3. Prompt user for MIDI input port selection (reuse existing select_input_port)
4. Prompt user for MIDI output port selection (reuse existing select_output_ports)
5. Prompt user for key, mode, octave_mode (reuse existing select_key, select_mode, select_octave_mode)
6. Send Configure message to server with selected key, mode, octave_mode, voice_count (= number of output ports)
7. Wait for Ack
8. Connect to local MIDI input (reuse connect_input with mpsc channel)
9. Create local OutputRouter for selected output ports
10. Spawn reader thread: loops reading messages from server via protocol::read_message(). For MidiData responses, route to local outputs using OutputRouter. Track which output port each harmonized note goes to (first = port 0, second = port 1, etc. - server sends them in order).
11. Main thread: loops reading from MIDI input channel (mpsc). For each MIDI message, send as MidiData via protocol::write_message(). Check for Enter key to stop (same pattern as CLI router).
12. On exit: send Disconnect message to server, close stream.

The client reuses existing MIDI port selection and output routing. The key difference from local mode: instead of processing through local HarmonyEngine, MIDI goes to server and harmonized results come back.

For the reader thread, track a simple counter: server sends N MidiData messages in response to one input note (one per voice). Route message i to output port i. Reset counter on each new input note. Simpler approach: just use a rotating index that wraps at voice_count.

Actually, simplest: server should send all harmonized notes for one input as separate MidiData messages. Client routes them round-robin to output ports. OR better: add a voice_index field.

Simplest viable approach: server sends harmonized notes in order (voice 0, voice 1, ...). Client tracks a per-input counter and routes accordingly. Since MIDI is serial and we process one note at a time, this works. Use an AtomicUsize counter shared between writer (resets on send) and reader (increments on receive, mod voice_count -> output port index).

Gate the client function with `#[cfg(not(feature = "gui"))]` since it needs terminal input for port selection. When GUI feature is enabled and --client is passed, print an error saying client mode requires CLI build.
