# Phase 6.5: Note Generator - Research

**Researched:** 2026-01-30
**Domain:** Virtual MIDI input source with beat-synced note generation (Rust/egui)
**Confidence:** HIGH

## Summary

This phase adds a virtual MIDI input source (Note Generator) that produces notes without requiring a physical MIDI device. It integrates with the existing BeatClock, feeds notes through the full harmony engine pipeline, and appears as a selectable option in the IN device dropdown.

The implementation is entirely internal to the existing codebase -- no new crates are needed. The generator is a Rust struct that produces `wmidi::Note` values on beat clock ticks, injected into the same processing path that physical MIDI input uses. The main architectural challenge is cleanly merging generator output with physical MIDI input, and providing UI controls for note/chord/pattern selection.

**Primary recommendation:** Create a `NoteGenerator` struct in a new `src/generator/` module that produces MIDI note events based on BeatClock ticks. Wire it as a virtual input source option alongside physical MIDI devices. Generator notes enter the same `engine.harmonize_note_on()` path as physical MIDI.

### Pattern 1: NoteGenerator as Virtual Input Source
**What:** A struct that produces `Vec<u8>` MIDI messages (same format as physical MIDI input) on each tick, driven by BeatClock.
**When to use:** Every frame in the update loop (WASM) or every router loop iteration (native).

```rust
/// Generator operating modes
#[derive(Clone, Debug, PartialEq)]
pub enum GeneratorMode {
    /// Hold specific notes continuously (user-selected)
    HeldNotes,
    /// Play a chord's notes simultaneously
    Chord(ChordType),
    /// Arpeggiate through notes: up, down, up-down
    Arpeggio(ArpDirection),
    /// Walk through scale degrees sequentially
    ScaleRunner,
    /// Random diatonic notes from current key
    RandomDiatonic,
}

#[derive(Clone, Debug, PartialEq)]
pub enum ArpDirection { Up, Down, UpDown }

pub struct NoteGenerator {
    mode: GeneratorMode,
    /// Notes currently selected (from UI: piano clicks or chord selection)
    selected_notes: Vec<wmidi::Note>,
    /// Notes currently sounding (need Note-Off tracking)
    active_notes: Vec<wmidi::Note>,
    /// Current position in arpeggio/scale sequence
    sequence_index: usize,
    /// Direction state for up-down arpeggio
    ascending: bool,
    /// Whether generator is enabled/active
    enabled: bool,
    /// Note duration in beats (e.g., 0.25 = sixteenth, 0.5 = eighth, 1.0 = quarter)
    note_duration_beats: f64,
    /// Track last beat position to detect note triggers
    last_beat_position: f64,
    /// Velocity for generated notes
    velocity: u8,
}
```

### Pattern 2: Virtual Input in Device Dropdown
**What:** Add "Note Generator" as a special entry in `available_inputs`. Use a sentinel value (e.g., `usize::MAX`) or an enum to distinguish it from physical ports.
**When to use:** When populating the IN device combo box.

```rust
// In AppState or device list population:
// Add virtual input as first entry
self.state.available_inputs.insert(0, (usize::MAX, "Note Generator".to_string()));

// When starting: check if input_port == usize::MAX
// If so, skip physical MIDI connection, use generator instead
```

### Pattern 3: Merging Generator + Physical Input
**What:** Both sources produce note events that feed into `engine.harmonize_note_on()`. The generator runs on beat clock ticks; physical MIDI arrives via callback/queue.
**When to use:** Success criterion 6 requires both sources running simultaneously.

For native: The router thread processes both `mpsc::Receiver` messages (physical) AND generator tick output each loop iteration.

For WASM: The `update()` frame loop already drains `midi_queue`. Add generator tick output to the same processing path.

```rust
// In router loop (native) or update() (WASM):
// 1. Tick generator
let gen_events = generator.tick(beat_position, now_ms);
for event in gen_events {
    process_midi_message(&event, ...);
}
// 2. Process physical MIDI (existing code)
```

**What:** User picks a chord name (Cmaj, Am7, etc.) and the generator resolves it to concrete notes using the current key.

### Anti-Patterns to Avoid
- **Separate MIDI processing path for generator:** Generator notes MUST go through the same `harmonize_note_on` pipeline as physical MIDI. Do NOT create a parallel processing path.
- **Generator running on its own thread (WASM):** WASM is single-threaded. Generator must tick synchronously in `update()`.
- **Forgetting Note-Off:** Every generated Note-On MUST have a corresponding Note-Off, or notes will get stuck. Track active notes and release them before sending new ones.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Beat position tracking | Custom timing | Existing `BeatClock` | Already handles BPM, time sig, beat crossings |
| MIDI message construction | Raw byte arrays | `wmidi::MidiMessage` | Already used everywhere, handles encoding |
| Scale degree lookup | Custom scale math | Existing `Scale` struct | Has `degree_of()`, `transpose()`, `notes_in_range()` |
| Note display | Custom note names | Existing `midi_to_name()` | Already handles MIDI-to-name conversion |
| Chord detection display | Custom chord display | Existing `chord_display()` | Generator notes will show up in piano + chord display automatically |

## Common Pitfalls

### Pitfall 1: Stuck Notes on Mode/Config Change
**What goes wrong:** Switching generator mode or notes while notes are sounding leaves Note-On without Note-Off.
**Why it happens:** Generator changes selected_notes mid-phrase without releasing old ones.
**How to avoid:** Always send Note-Off for all active_notes before changing mode or selected notes. Implement an `all_notes_off()` method.
**Warning signs:** Notes sustaining indefinitely after UI changes.

### Pitfall 2: Beat Clock Not Running
**What goes wrong:** Generator produces no output because BeatClock hasn't been started.
**Why it happens:** BeatClock starts on first running frame (existing behavior). If generator is enabled before Start is clicked, nothing happens.
**How to avoid:** Generator should check `clock.running` before producing notes. Generator only produces when the app is running.

### Pitfall 3: Double-Processing in Dual Input Mode
**What goes wrong:** When both physical MIDI and generator are active, notes get processed twice or routing conflicts occur.
**Why it happens:** Both sources call `harmonize_note_on()` on the same engine instance.
**How to avoid:** This is actually fine -- the harmony engine tracks notes by input note value. Physical and generator notes are independent inputs. Just ensure Note-Off tracking is separate for each source.

### Pitfall 4: WASM vs Native Divergence
**What goes wrong:** Generator works on native but not WASM (or vice versa).
**Why it happens:** Native uses router thread; WASM uses frame-based polling.
**How to avoid:** NoteGenerator struct itself should be platform-independent. Only the integration point differs:
- Native: generator ticked in router thread loop
- WASM: generator ticked in `update()` alongside existing WASM MIDI processing

### Pitfall 5: Note Duration Timing
**What goes wrong:** Notes are too short or overlap because duration calculation is wrong.
**Why it happens:** Beat-based duration needs conversion to milliseconds using current BPM.
**How to avoid:** Use `note_duration_beats * (60000.0 / bpm)` for millisecond duration. Track note-on time and schedule note-off accordingly.

## Code Examples

### Generator Tick (beat-synced note production)
```rust
impl NoteGenerator {
    /// Called each frame/loop iteration. Returns MIDI events to process.
    /// `beat_pos` is current fractional beat position within bar (0.0 to beats_per_bar).
    pub fn tick(&mut self, beat_pos: f64, bpm: f64) -> Vec<GeneratorEvent> {
        if !self.enabled || self.selected_notes.is_empty() {
            return vec![];
        }

        let mut events = Vec::new();
        let step_size = self.note_duration_beats;

        // Quantize to step grid
        let current_step = (beat_pos / step_size).floor();
        let last_step = (self.last_beat_position / step_size).floor();

        if current_step != last_step {
            // Release previous notes
            for &note in &self.active_notes {
                events.push(GeneratorEvent::NoteOff(note));
            }
            self.active_notes.clear();

            // Generate new notes based on mode
            let new_notes = match &self.mode {
                GeneratorMode::HeldNotes => self.selected_notes.clone(),
                GeneratorMode::Arpeggio(dir) => {
                    vec![self.next_arp_note(dir)]
                }
                GeneratorMode::ScaleRunner => {
                    vec![self.next_scale_note()]
                }
                GeneratorMode::RandomDiatonic => {
                    vec![self.random_diatonic_note()]
                }
                GeneratorMode::Chord(_) => self.selected_notes.clone(),
            };

            for note in &new_notes {
                events.push(GeneratorEvent::NoteOn(*note, self.velocity));
                self.active_notes.push(*note);
            }
        }

        self.last_beat_position = beat_pos;
        events
    }
}

pub enum GeneratorEvent {
    NoteOn(wmidi::Note, u8),  // note, velocity
    NoteOff(wmidi::Note),
}
```

### Integration into WASM update loop
```rust
// In ContrapunkApp::update(), after beat clock tick, before physical MIDI drain:
if self.state.is_running && self.generator.enabled {
    let beat_pos = self.wasm_humanizer.clock().beat_position;  // or similar accessor
    let bpm = self.humanize_config.bpm;
    let events = self.generator.tick(beat_pos, bpm);
    for event in events {
        match event {
            GeneratorEvent::NoteOn(note, vel) => {
                // Feed through same path as physical MIDI
                let velocity = Velocity::try_from(vel).unwrap_or(Velocity::MAX);
                self.handle_wasm_note_on(Channel::Ch1, note, velocity);
            }
            GeneratorEvent::NoteOff(note) => {
                self.handle_wasm_note_off(Channel::Ch1, note, Velocity::MIN);
            }
        }
    }
}
```

## Open Questions

1. **Piano keyboard click interaction**
   - What we know: Piano keyboard is in BottomPanel, always visible. Currently display-only.
   - What's unclear: Best UX for toggling between "display mode" and "select mode" for the piano. Should clicks always work when generator is selected as input?
   - Recommendation: When "Note Generator" is selected as IN device, piano keys become clickable to select notes. Visual indicator (different highlight color) distinguishes selected vs. sounding notes.

2. **Chord selection UI**
   - What we know: Need to select root note + chord quality (Cmaj, Am7, etc.)
   - What's unclear: How much chord selection complexity to expose. Full chord browser vs. simple root+quality dropdown.
   - Recommendation: Two dropdowns -- root note (C through B) + chord quality (Major, Minor, Dom7, etc.). This is compact and fits the existing UI style.

3. **Generator + Physical MIDI simultaneous use**
   - What we know: Success criterion 6 requires both sources to merge.
   - What's unclear: Should both be selectable simultaneously, or should there be a "merge" option?
   - Recommendation: Allow generator to be toggled ON independently of input device selection. When both are active, both feed into the engine. This avoids complicating the dropdown.
