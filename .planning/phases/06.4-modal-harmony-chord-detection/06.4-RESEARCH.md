**Researched:** 2026-01-31

## Summary

This phase extends the existing custom Rust music theory engine with modal scales, modal interchange, and comprehensive chord detection. There are no external libraries to evaluate — the project has a fully hand-rolled harmony engine (`src/harmony/`) and chord detector (`src/chord.rs`). The work is pure music theory implementation in Rust.

The existing `Scale` struct uses a hardcoded `[u8; 7]` offsets array (major scale only). It needs to support 9 scale types. The `HarmonyEngine` currently calls `Scale::major(tonic)` — this must be parameterized by a `ScaleMode` enum. The chord detector (`chord.rs`) has only 12 patterns (triads + 7ths + power chords) — it needs ~40+ patterns for extended/altered/slash/add chords.

**Primary recommendation:** Add a `ScaleMode` enum to `config.rs`, extend `Scale` to accept arbitrary 7-note offsets, add modal interchange logic as a new method on `Scale` (replacing `harmonize_chromatic`), and massively expand `CHORD_PATTERNS` in `chord.rs` with slash chord and roman numeral analysis.

## Architecture Patterns

### Pattern 1: ScaleMode Enum (mirrors existing Key/HarmonyMode pattern)
**What:** Add `ScaleMode` enum to `config.rs` following the exact pattern of `Key` and `HarmonyMode`
**When to use:** All scale mode selection

```rust

pub enum ScaleMode {

    Dorian,        // [0, 2, 3, 5, 7, 9, 10]

    Lydian,        // [0, 2, 4, 6, 7, 9, 11]
    Mixolydian,    // [0, 2, 4, 5, 7, 9, 10]
    Aeolian,       // [0, 2, 3, 5, 7, 8, 10] — natural minor
    Locrian,       // [0, 1, 3, 5, 6, 8, 10]
    HarmonicMinor, // [0, 2, 3, 5, 7, 8, 11]
    MelodicMinor,  // [0, 2, 3, 5, 7, 9, 11] — ascending form
```

### Pattern 2: Scale Construction from ScaleMode
**What:** Replace `Scale::major(tonic)` with `Scale::new(tonic, mode)`
**Key insight:** The `offsets: [u8; 7]` field already supports any 7-note scale. Just need a constructor.

```rust
impl Scale {
    pub fn new(tonic: u8, mode: ScaleMode) -> Self {
        Self {
            tonic: tonic % 12,
            offsets: mode.intervals(),
        }
    }
    // Keep Scale::major() as backward-compatible alias
    pub fn major(tonic: u8) -> Self {
        Self::new(tonic, ScaleMode::Ionian)
    }
}
```

### Pattern 3: Modal Interchange as Scale Method
**What:** Replace `harmonize_chromatic()` with modal interchange lookup
**Key insight:** The current `harmonize_chromatic` in `scale.rs` lines 158-182 is the exact place to insert modal interchange. When a note is out-of-key, instead of trying consonant intervals, look up which parallel mode contains that note and borrow from it.

```rust
/// Modal interchange: find the best parallel mode that contains this note
pub fn find_borrowing_source(&self, note: Note, available_modes: &[ScaleMode]) -> Option<(ScaleMode, Scale)> {
    let pitch_class = u8::from(note) % 12;
    for &mode in available_modes {
        let parallel = Scale::new(self.tonic, mode);
        if parallel.degree_of_pc(pitch_class).is_some() {
            return Some((mode, parallel));
        }
    }
    None
}
```

### Pattern 4: Borrowing Range Slider -> Mode Unlocking Order
**What:** Progressive mode unlocking for the 1-5 slider
**Recommended order (Claude's discretion):**

| Slider | Modes Available for Borrowing |
|--------|-------------------------------|
| 1 | Aeolian (parallel minor) |
| 2 | + Dorian |
| 3 | + Mixolydian, Lydian |
| 4 | + Phrygian, Harmonic Minor |
| 5 | + Locrian, Melodic Minor (all 9) |

**Rationale:** Ordered by commonality in classical/jazz borrowing. Parallel minor is the most common source of borrowed chords, Dorian next (jazz), then increasingly chromatic.

### Anti-Patterns to Avoid
- **Separate scale structs per mode:** Use the same `Scale` struct with different offsets — all modes are just different interval patterns on the same 7-degree structure
- **Hardcoding mode intervals in multiple places:** Define intervals once on `ScaleMode::intervals()`, use everywhere
- **Modifying melody notes:** Modal interchange only affects harmony generation, never the user's input

## Common Pitfalls

### Pitfall 1: Breaking Ionian Default
**What goes wrong:** Adding ScaleMode changes behavior for users who haven't selected a mode
**Why it happens:** If `Scale::major()` is changed or default mode isn't Ionian
**How to avoid:** Default `ScaleMode` to `Ionian`. `Scale::major()` must remain and produce identical results. Add `#[default]` to `Ionian` variant.
**Warning signs:** Existing tests fail after adding ScaleMode

### Pitfall 2: Melodic Minor Ascending vs Descending
**What goes wrong:** Melodic minor has different ascending (raised 6th and 7th) and descending (natural minor) forms
**Why it happens:** Classical melodic minor is directional
**How to avoid:** Use ascending form only (jazz convention). Document this. The descending form is just Aeolian, which is already available as a separate mode.
**Warning signs:** Users expect descending melodic minor behavior

### Pitfall 3: Chord Detection Combinatorial Explosion
**What goes wrong:** With 5-6 note chords, trying every pitch class as root with every pattern becomes slow
**Why it happens:** O(n * p) where n = pitch classes, p = patterns — fine for small sets but patterns grow
**How to avoid:** Keep patterns ordered by length (longest first, already done). Short-circuit on match. The search space is small (max 12 pitch classes * ~50 patterns = 600 checks) — no real performance concern.
**Warning signs:** N/A — this won't actually be slow

### Pitfall 4: Slash Chord vs Inversion Confusion
**What goes wrong:** C/E could mean "C major with E in bass" (first inversion) or a true slash chord
**Why it happens:** Same notation, different musical meaning
**How to avoid:** If the bass note is part of the chord, show it as an inversion slash chord (standard notation). If bass note is NOT part of the chord, it's a polychord situation — show as "X/Y".
**Warning signs:** Displaying inversions as if they're different chords

### Pitfall 5: Modal Interchange Tie-Breaking
**What goes wrong:** An out-of-key note exists in multiple parallel modes — which do we borrow from?
**Why it happens:** e.g., Bb in C major exists in C Dorian, C Mixolydian, C Aeolian, etc.
**How to avoid:** Priority order: prefer the mode that shares the most notes with the current scale (closest mode). For equal cases, prefer modes earlier in the borrowing range slider order.
**Warning signs:** Inconsistent "borrowed from" labels for the same note in different contexts

### Pitfall 6: Enharmonic Spelling in Chord Names
**What goes wrong:** Showing "C# major" when user is in Db major context
**Why it happens:** Using sharp-only note names regardless of key
**How to avoid:** The `is_flat_key()` function must be used consistently in both chord detection output AND piano key labels AND the borrowed-from indicator.
**Warning signs:** Mixing sharps and flats in the same display

### Slash Chord Detection Logic
```rust
pub fn detect_chord_full(notes: &HashSet<u8>, key: Key) -> ChordInfo {
    // 1. Get pitch classes
    let mut pcs: Vec<u8> = notes.iter().map(|n| n % 12).collect();
    pcs.sort(); pcs.dedup();

    // 2. Find actual lowest note (not pitch class — use original MIDI)
    let bass_midi = *notes.iter().min().unwrap();
    let bass_pc = bass_midi % 12;

    // 3. Try pattern matching with each PC as root
    if let Some((root, name)) = find_best_pattern(&pcs) {
        let root_name = note_name(root, key);
        let chord_name = if bass_pc != root {
            let bass_name = note_name(bass_pc, key);
            format!("{}{}/{}", root_name, name, bass_name) // Slash chord
        } else {
            format!("{}{}", root_name, name)
        };
        // 4. Roman numeral analysis
        let roman = roman_numeral(root, &name, key);
        ChordInfo { name: chord_name, roman: Some(roman), .. }
    } else {
        // Ambiguous — show intervals
        ChordInfo { name: format_intervals(&pcs, key), roman: None, .. }
    }
}
```

### Roman Numeral Analysis
```rust
fn roman_numeral(root_pc: u8, quality: &str, key: Key, scale_mode: ScaleMode) -> String {
    let scale = Scale::new(key.semitones_from_c(), scale_mode);
    let degree = scale.degree_of_pc(root_pc);
    let numerals = ["I", "II", "III", "IV", "V", "VI", "VII"];

    match degree {
        Some(d) => {
            let numeral = numerals[d];
            // Lowercase for minor/diminished qualities
            let numeral = if quality.starts_with("min") || quality.starts_with("dim") || quality == "m7b5" {
                numeral.to_lowercase()
            } else {
                numeral.to_string()
            };
            format!("{}{}", numeral, quality)
        }
        None => String::new() // Chromatic root — no roman numeral
    }
}
```

## Open Questions

1. **Chord detection with omitted notes**
   - What we know: Real-world voicings often omit the 5th in 7th chords, or the root in extensions
   - What's unclear: How aggressively to match partial voicings (too aggressive = false positives)
   - Recommendation: Start with exact match only; add "fuzzy" matching later if too many unrecognized chords

2. **Melodic minor ascending-only convention**
   - What we know: Jazz uses ascending form; classical uses ascending/descending
   - What's unclear: Whether users will expect descending behavior
   - Recommendation: Use ascending only, label as "Melodic Minor (ascending)" in the dropdown

3. **Performance of expanded chord detection**
   - What we know: Current approach is O(pitch_classes * patterns), patterns growing ~4x
   - What's unclear: Whether this matters in real-time MIDI context
   - Recommendation: Profile if needed, but 12 * 50 = 600 comparisons per chord is trivially fast
