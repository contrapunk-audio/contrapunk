## Summary

This phase replaces the entire egui/eframe GUI with a Tauri v2 + SvelteKit + Svelte 5 frontend while keeping the Rust harmony engine as a backend library. The same Svelte app runs in both a Tauri desktop webview and directly in the browser (with Rust core compiled to WASM). This is a full rewrite of the rendering layer with a dramatic visual identity shift from PICO-8 retro green to Hyper Light Drifter's deep indigo/magenta/teal/cyan neon aesthetic, combined with Ableton Live Session View's grid-based DAW layout.

The architecture splits into two communication paths: desktop (Tauri IPC commands) and browser (wasm-bindgen). A TypeScript adapter layer abstracts this so Svelte components call the same API regardless of platform. The Rust core (harmony engine, MIDI routing, humanizer, beat clock, presets) remains intact with minimal surface changes.

**Primary recommendation:** Use Tauri v2 + SvelteKit (adapter-static, SPA mode) + Svelte 5 runes + Tailwind CSS v4 + wasm-pack for the WASM build. Build a thin TypeScript adapter layer that provides a unified API over Tauri IPC (desktop) and wasm-bindgen (browser). Custom-build all visual components to achieve the HLD pixel art aesthetic — no off-the-shelf component library will match this visual identity.

### Pattern 1: Platform Adapter Layer (RECOMMENDED)

**What:** A TypeScript abstraction that provides a single API surface over two backends — Tauri IPC commands (desktop) and wasm-bindgen direct calls (browser).

**When to use:** Every Svelte component that needs to call Rust code. Components never call Tauri invoke() or WASM functions directly.

**Why:** The same Svelte app runs in both Tauri webview and bare browser. Without this layer, every component would need `if (isTauri) { ... } else { ... }` conditionals.

**Example:**
```typescript
// ui/src/lib/adapter/types.ts
export interface ContrapunkAdapter {
  // Engine control
  getEngineState(): Promise<EngineState>;
  setKey(key: string): Promise<void>;
  setMode(mode: string): Promise<void>;
  setScaleMode(mode: string): Promise<void>;
  setOctaveMode(mode: string): Promise<void>;
  setVoiceLeading(enabled: boolean, style: string): Promise<void>;

  // MIDI
  listMidiInputs(): Promise<MidiDevice[]>;
  listMidiOutputs(): Promise<MidiDevice[]>;
  connectInput(deviceId: string): Promise<void>;
  connectOutputs(deviceIds: string[]): Promise<void>;

  // Routing
  startRouting(): Promise<void>;
  stopRouting(): Promise<void>;

  // State subscriptions (real-time note updates)
  onNoteUpdate(callback: (notes: NoteState) => void): () => void;

  // Presets
  listPresets(): Promise<Preset[]>;
  savePreset(name: string): Promise<void>;
  loadPreset(name: string): Promise<void>;
}

// ui/src/lib/adapter/tauri.ts
import { invoke } from '@tauri-apps/api/core';
import { listen } from '@tauri-apps/api/event';

export class TauriAdapter implements ContrapunkAdapter {
  async setKey(key: string): Promise<void> {
    await invoke('set_key', { key });
  }

  onNoteUpdate(callback: (notes: NoteState) => void): () => void {
    let unlisten: (() => void) | undefined;
    listen<NoteState>('note-update', (event) => {
      callback(event.payload);
    }).then(fn => unlisten = fn);
    return () => unlisten?.();
  }
  // ...
}

// ui/src/lib/adapter/wasm.ts
import init, { create_engine, set_key, /* ... */ } from '../../wasm-pkg';

export class WasmAdapter implements ContrapunkAdapter {
  private initialized = false;

  async setKey(key: string): Promise<void> {
    if (!this.initialized) { await init(); this.initialized = true; }
    set_key(key);
  }
  // ...
}

// ui/src/lib/adapter/index.ts
import { TauriAdapter } from './tauri';
import { WasmAdapter } from './wasm';

function isTauri(): boolean {
  return typeof window !== 'undefined' && '__TAURI__' in window;
}

export const adapter: ContrapunkAdapter = isTauri()
  ? new TauriAdapter()
  : new WasmAdapter();
```

### Pattern 2: Svelte 5 Runes for Shared State

**What:** Use `.svelte.ts` files with `$state` runes for reactive global state shared across components.

**When to use:** Any state that multiple components need (current key, active notes, running status, UI preferences).

**Example:**
```typescript
// ui/src/lib/stores/engine.svelte.ts
import { adapter } from '$lib/adapter';

class EngineStore {
  key = $state('C');
  mode = $state('PassThrough');
  scaleMode = $state('Ionian');
  octaveMode = $state('None');
  isRunning = $state(false);
  inputNotes = $state<number[]>([]);
  harmonyNotes = $state<number[]>([]);
  borrowedNotes = $state<number[]>([]);
  chordName = $state('');

  async setKey(key: string) {
    await adapter.setKey(key);
    this.key = key;
  }

  async start() {
    await adapter.startRouting();
    this.isRunning = true;
  }
}

export const engine = new EngineStore();
```

### Pattern 3: Tauri Command Definitions

**What:** Rust functions decorated with `#[tauri::command]` that expose the harmony engine to the frontend.

**When to use:** Every backend operation in the desktop build.

**Example:**
```rust
// src-tauri/src/commands/harmony.rs
use tauri::State;
use std::sync::Mutex;
use contrapunk::harmony::{Key, HarmonyMode, HarmonyEngine};

pub struct AppState {
    pub engine: Mutex<HarmonyEngine>,
    // ... other state
}

#[tauri::command]
pub fn set_key(key: String, state: State<AppState>) -> Result<(), String> {
    let key = Key::from_str(&key).map_err(|e| e.to_string())?;
    state.engine.lock().unwrap().set_key(key);
    Ok(())
}

#[tauri::command]
pub fn get_engine_state(state: State<AppState>) -> Result<EngineState, String> {
    let engine = state.engine.lock().unwrap();
    Ok(EngineState {
        key: engine.key().to_string(),
        mode: engine.mode().to_string(),
        // ...
    })
}
```

### Pattern 4: Real-Time Note Updates via Tauri Events

**What:** Use Tauri's event system to push note state changes from Rust router thread to Svelte frontend at frame rate.

**When to use:** Active notes, harmony notes, chord detection — anything that changes at note-on/note-off speed.

**Why:** Commands are request-response. For real-time note display, the backend needs to push updates to the frontend.

**Example:**
```rust
// In router thread
use tauri::Emitter;

// Every ~16ms (60fps) or on note change:
app_handle.emit("note-update", NoteState {
    input_notes: vec![60, 64],
    harmony_notes: vec![67, 72],
    chord_name: "Cmaj".to_string(),
    borrowed_notes: vec![],
}).unwrap();
```

```typescript
// In Svelte component
import { listen } from '@tauri-apps/api/event';
import { onMount, onDestroy } from 'svelte';
import { engine } from '$lib/stores/engine.svelte';

let unlisten: (() => void) | undefined;

onMount(async () => {
  unlisten = await listen('note-update', (event) => {
    engine.inputNotes = event.payload.input_notes;
    engine.harmonyNotes = event.payload.harmony_notes;
    engine.chordName = event.payload.chord_name;
  });
});

onDestroy(() => unlisten?.());
```

### Anti-Patterns to Avoid
- **Calling Tauri invoke() directly from components:** Always go through the adapter layer. Direct invoke() calls make browser deployment impossible.
- **Using Svelte stores (legacy $: syntax) instead of runes:** Svelte 5 runes ($state, $derived, $effect) are the future. Stores still work but mixing paradigms creates confusion.
- **SSR in SvelteKit with Tauri:** Tauri does not support server-side rendering. Set `export const ssr = false` in root layout. Use adapter-static with SPA fallback.
- **Polling for note state:** Use Tauri events (push) for real-time note display, not repeated invoke() calls (pull). The ~0.5ms invoke latency would compound at 60fps.
- **Monolithic CSS files:** Use Tailwind utilities for layout/spacing and CSS custom properties for the HLD color system. Avoid a single massive stylesheet.
- **Pixel art with `<canvas>` for UI elements:** Use CSS `image-rendering: pixelated` for images and SVGs. Only use `<canvas>` for the particle system and any actual animation layers.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Particle effects | Custom canvas particle system | @tsparticles/svelte + @tsparticles/slim | Hundreds of configuration options, performance-optimized, tree-shakeable. Custom would take days for the same quality. |
| WASM-JS interop | Manual JS glue code | wasm-bindgen + wasm-pack | Handles memory management, type conversion, error propagation. Hand-rolling this is error-prone and fragile. |
| Tauri IPC types | Manual serialization | serde + tauri::command derive | Tauri auto-serializes/deserializes command args and return values via serde. |
| CSS utility classes | Custom utility stylesheet | Tailwind CSS v4 | Thousands of responsive, state-aware utilities. Custom utilities drift and become inconsistent. |
| MIDI device listing | Custom platform detection | tauri-plugin-midi (desktop) + navigator.requestMIDIAccess (browser) | Platform-specific MIDI APIs are complex. Existing solutions handle permissions, enumeration, hot-plug. |
| Piano keyboard layout | Calculate key positions manually | Precomputed lookup table (like current PianoKeyboard) | The 88-key layout with black key offsets is well-understood. Port the existing logic to SVG/CSS. |
| State management | Custom pub/sub system | Svelte 5 runes ($state in .svelte.ts files) | Built into the framework. Fine-grained reactivity with zero boilerplate. |

**Key insight:** This phase's complexity is in the architectural wiring (adapter layer, build pipeline, deployment) and the visual design system. The Rust core stays intact. Don't waste time on solved problems.

## Common Pitfalls

### Pitfall 1: IPC Serialization Overhead for Real-Time Data
**What goes wrong:** Sending note state via Tauri commands (invoke) at 60fps creates serialization bottleneck. Each invoke serializes to JSON, crosses the IPC bridge (~0.5ms), and deserializes.
**Why it happens:** Developers treat commands like function calls. They're closer to HTTP requests in latency terms.
**How to avoid:** Use Tauri events for push-based note state updates. Batch updates (send one event per frame with all note state, not one per note-on/off). Consider using Tauri's raw IPC (binary) for large payloads.
**Warning signs:** Piano keyboard flickering, delayed note display, CPU spike from serialization.

### Pitfall 2: WASM Module Initialization Race Condition
**What goes wrong:** Svelte components try to call WASM functions before the WASM module is initialized.
**Why it happens:** WASM init is async. If components mount before init completes, calls fail silently or crash.
**How to avoid:** Initialize WASM in onMount of root layout. Gate all adapter calls behind an `initialized` promise. Show loading state until ready.
**Warning signs:** "wasm not initialized" errors, blank UI on first load, intermittent failures.

### Pitfall 3: Two Build Systems Diverging
**What goes wrong:** Desktop build (Tauri + Vite) and browser build (SvelteKit build + wasm-pack) produce different behavior because they use different Rust code paths.
**Why it happens:** Desktop Rust code runs natively in src-tauri; browser Rust code runs as WASM from wasm-pkg. Different feature flags, different compilation.
**How to avoid:** Extract shared Rust core as a library crate. Both src-tauri and wasm-pkg depend on the same `contrapunk` core. Run tests against the core crate directly. CI builds both targets.
**Warning signs:** "Works on desktop but not browser" bugs.

### Pitfall 4: Pixel Art Rendering Blurry at Non-Integer Scales
**What goes wrong:** Pixel art icons, fonts, and UI elements look blurry because the browser applies bilinear interpolation when scaling.
**Why it happens:** Default `image-rendering: auto` smooths pixels. CSS transforms with non-integer scales cause sub-pixel rendering.
**How to avoid:** Use `image-rendering: pixelated` on all pixel art elements. Scale pixel art at integer multiples only (2x, 3x, 4x). Use Press Start 2P font at multiples of 8px (8, 16, 24, 32). Avoid CSS transforms with fractional values.
**Warning signs:** Fuzzy edges on pixel art, font rendering looks "soft" instead of crisp.

### Pitfall 5: Tailwind Purging Removes Dynamic Classes
**What goes wrong:** Tailwind's tree-shaking removes CSS classes that are constructed dynamically (e.g., `bg-${color}-500`).
**Why it happens:** Tailwind scans source files for class names at build time. Dynamic string interpolation is invisible to the scanner.
**How to avoid:** Use complete class names in source code. For dynamic theming, use CSS custom properties (`style="--accent: {color}"`) rather than dynamic Tailwind classes. Define a safelist for known dynamic classes if unavoidable.
**Warning signs:** Missing styles in production but working in dev.

### Pitfall 6: Web MIDI API Browser Support Limitations
**What goes wrong:** MIDI devices don't work in Firefox or Safari, only in Chromium-based browsers.
**Why it happens:** Web MIDI API (`navigator.requestMIDIAccess()`) is only supported in Chrome, Edge, Opera, and Brave. Firefox and Safari do not implement it.
**How to avoid:** Detect Web MIDI support on load. Show clear browser compatibility message. Consider JZZ library as a polyfill (adds Jazz-Plugin fallback). For non-MIDI browsers, the app still works with computer keyboard input and the note generator.
**Warning signs:** "requestMIDIAccess is not a function" errors, users reporting MIDI doesn't work.

### Pitfall 7: SvelteKit Adapter-Static + Tauri Configuration Mismatch
**What goes wrong:** Tauri can't find the built frontend, or SvelteKit generates server-side code that fails in Tauri's webview.
**Why it happens:** SvelteKit defaults to SSR. Tauri expects a static build directory.
**How to avoid:** Set `export const ssr = false` in `src/routes/+layout.ts`. Use adapter-static with `fallback: 'index.html'` for SPA mode. Point Tauri's `frontendDist` to `../ui/build`. Point `devUrl` to `http://localhost:5173`.
**Warning signs:** Blank white screen in Tauri window, "document is not defined" errors.

### Piano Keyboard in Svelte (88-key, HLD-styled)
```svelte
<!-- ui/src/lib/components/Piano.svelte -->
<script lang="ts">
  import { engine } from '$lib/stores/engine.svelte';

  const PIANO_START = 21;  // A0
  const PIANO_END = 108;   // C8

  function isBlackKey(midi: number): boolean {
    return [1,3,6,8,10].includes(midi % 12);
  }

  function keyColor(midi: number): string {
    if (engine.inputNotes.includes(midi)) return 'var(--color-piano-input)';
    if (engine.harmonyNotes.includes(midi)) return 'var(--color-piano-harmony)';
    if (engine.borrowedNotes.includes(midi)) return 'var(--color-piano-borrowed)';
    return '';
  }

  const whiteKeys = Array.from({length: PIANO_END - PIANO_START + 1}, (_, i) => i + PIANO_START)
    .filter(n => !isBlackKey(n));
  const blackKeys = Array.from({length: PIANO_END - PIANO_START + 1}, (_, i) => i + PIANO_START)
    .filter(n => isBlackKey(n));
</script>

<div class="piano-container">
  <!-- White keys -->
  {#each whiteKeys as midi}
    <div
      class="white-key"
      style:background={keyColor(midi) || 'var(--color-text-primary)'}
      style:box-shadow={engine.inputNotes.includes(midi) ? 'var(--glow-teal)' : 'none'}
    ></div>
  {/each}
  <!-- Black keys positioned absolutely -->
  {#each blackKeys as midi}
    <div
      class="black-key"
      style:background={keyColor(midi) || '#111'}
    ></div>
  {/each}
</div>
```

## Visual Identity: HLD + Ableton Design System

### Hyper Light Drifter Visual Language
- **Color philosophy:** Emotional weight through deep cool backgrounds with vibrant warm neon accents. Not flat — uses gradients and vignettes for depth.
- **Palette zones:** Deep indigo/navy (#0a0a1a to #1a1833) backgrounds. Magenta/pink (#ff3388, #ff77aa) as primary accent. Cyan/teal (#33ddff, #00ccaa) as secondary. Amber/gold (#ffaa33, #ffdd44) for warmth.
- **Pixel discipline:** Actual aliased edges, integer scaling, blocky fonts at 8px multiples. No anti-aliasing on decorative elements.
- **Atmosphere:** Glow effects (CSS box-shadow/text-shadow with color spread), light bloom (layered semi-transparent overlays), floating particles (tsParticles with slow drift, low count, neon colors), sense of depth (layered backgrounds with subtle parallax or gradient shifts).
- **HUD style:** Minimal, clean, icon-heavy. Simple geometric shapes. Dense information without clutter. Health-bar-style meters for levels/sliders.

### Ableton Live Session View Layout Patterns
- **Grid-based:** Tracks as columns, clips/scenes as rows. Dense but organized.
- **Color-coded sections:** Each track/group has a distinct color for quick identification.
- **Always-visible controls:** Transport (play/stop), master volume, tempo always accessible.
- **Compact controls:** Small knobs, mini faders, condensed dropdowns. Information density over whitespace.
- **Real-time feedback:** Clip launch animations, level meters, beat position indicators.

### Combined Design Language for Contrapunk
- **Layout:** Ableton-inspired grid. Left panel for MIDI/preset controls. Center for harmony configuration (key, mode, scale, voice leading). Right for humanization and generator. Bottom for sacred 88-key piano. Top bar for transport/status.
- **Aesthetic:** HLD's neon-on-dark palette. Pixel art icons and fonts. Glow effects on active/selected elements. Particle atmosphere behind the main UI. Ambient pulse animations tied to beat clock.
- **Interaction:** Pixel-perfect button presses (no hover transitions — instant state change like a game). Grid-based selector layouts. Minimal use of dropdowns — prefer visible grids of options (like Ableton's clip grid).

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Trunk + egui WASM | SvelteKit + wasm-pack | This phase | Trunk built entire Rust app as WASM including GUI. New approach: Svelte renders UI, only core logic goes to WASM. Much smaller WASM payload. |

| JSON-only Tauri IPC | Raw binary IPC option | Tauri v2 | For large payloads, can bypass JSON serialization. Useful for future audio data transfer. |

**Deprecated/outdated:**
- **Trunk** for WASM builds: Still works but unnecessary when using SvelteKit + wasm-pack. Trunk is for pure-Rust WASM apps.
- **Svelte stores** (writable/readable): Not deprecated but superseded by runes for most use cases in Svelte 5.
- **Tauri v1**: Still maintained but v2 is the recommended version for new projects.

## Open Questions

1. **tauri-plugin-midi maturity**
   - What we know: v1.0.5 exists, uses midir, emulates WebMIDI API. Small project (12 stars, 2 contributors).
   - What's unclear: Whether it handles all edge cases (hot-plug, multiple ports, SysEx). Whether it's actively maintained.
   - Recommendation: Start with tauri-plugin-midi. If it falls short, fall back to writing custom Tauri commands that directly use the existing midir code from the Rust core. The existing `midi::ports` module already handles all MIDI operations — wrapping it in Tauri commands is straightforward.

2. **WASM binary size after splitting core from GUI**
   - What we know: Current Trunk build produces the full app as WASM. New approach only compiles harmony engine + MIDI to WASM, which should be much smaller.
   - What's unclear: Exact size. The harmony engine has many modes and scales.
   - Recommendation: Build early, measure. Target < 500KB gzipped for the WASM payload. Use `wasm-opt` in the build pipeline.

3. **Real-time note update latency in browser vs desktop**
   - What we know: Desktop Tauri events have ~0.5ms overhead. Browser WASM calls are near-zero (same thread). But browser MIDI (WebMIDI) has its own latency.
   - What's unclear: Whether the event-based note update pattern introduces visible latency on the piano keyboard.
   - Recommendation: Prototype the note update loop early. If Tauri events are too slow, consider using Tauri channels (streaming responses) instead.

4. **Fly.io deployment with SvelteKit static build**
   - What we know: Current setup uses Trunk -> dist/ -> nginx on Fly.io. New setup would use SvelteKit build -> build/ + wasm-pack output -> nginx on Fly.io.
   - What's unclear: Whether the Fly.io Dockerfile and nginx config need significant changes.
   - Recommendation: Should be minimal. Update the Dockerfile to copy `ui/build/` instead of `dist/`. Ensure wasm-pack output is included in the SvelteKit build output.

5. **Press Start 2P font vs HLD-style alternatives**
   - What we know: Press Start 2P is currently embedded and works well. It's based on 1980s Namco arcade font. HLD uses its own custom pixel font that's slightly more refined.
   - What's unclear: Whether Press Start 2P fits the HLD aesthetic or if a different pixel font would be better.
   - Recommendation: Keep Press Start 2P initially. It's already working and OFL-licensed. Evaluate alternatives during the visual polish phase if the aesthetic doesn't gel.
