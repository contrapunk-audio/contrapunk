# Phase 5.1: WASM and In-Browser Support - Research

**Researched:** 2026-01-29
**Domain:** Rust WASM compilation, eframe web deployment, Web MIDI API, Fly.io static hosting
**Confidence:** MEDIUM

## Summary

This phase compiles Contrapunk to WebAssembly so it runs in a browser with MIDI device access. The existing codebase is well-structured for this: the GUI uses eframe (which has built-in WASM support via `eframe::WebRunner`), and midir already supports Web MIDI as a backend. The main challenges are: (1) abstracting MIDI I/O behind a trait so native midir and Web MIDI code paths coexist, (2) replacing `std::thread` usage in the router with WASM-compatible async patterns, (3) creating the web entry point with Trunk build tooling, and (4) deploying the static output to Fly.io via nginx.

The critical architectural insight is that **threads do not exist in WASM**. The current GUI router spawns a `std::thread` to run the MIDI routing loop. In WASM, this must become single-threaded async or run on the main thread with requestAnimationFrame-style polling. eframe's `update()` loop naturally provides a place to poll for MIDI messages each frame.

**Primary recommendation:** Add a `wasm` feature flag, abstract MIDI I/O behind a trait, replace thread-based routing with frame-based polling in WASM mode, use Trunk for building, deploy as static site on Fly.io with nginx.

### Pattern 1: MIDI Backend Trait Abstraction
**What:** Define a trait for MIDI operations that both native (midir) and web (web-sys) implement.
**When to use:** All MIDI I/O code paths.
**Example:**
```rust
// src/midi/mod.rs
pub trait MidiBackend {
    type InputConnection;
    type OutputConnection;

    fn list_inputs() -> Result<Vec<(usize, String)>>;
    fn list_outputs() -> Result<Vec<(usize, String)>>;
    fn connect_input(port: usize, callback: Box<dyn Fn(Vec<u8>) + Send>) -> Result<Self::InputConnection>;
    fn connect_output(port: usize) -> Result<Self::OutputConnection>;
    fn send_output(conn: &Self::OutputConnection, data: &[u8]) -> Result<()>;
}

#[cfg(not(target_arch = "wasm32"))]
mod native;
#[cfg(not(target_arch = "wasm32"))]
pub use native::*;

#[cfg(target_arch = "wasm32")]
mod web;
#[cfg(target_arch = "wasm32")]
pub use web::*;
```

### Pattern 2: Frame-Based MIDI Polling (WASM)
**What:** Instead of spawning a thread with `recv_timeout`, poll for MIDI messages each frame in eframe's `update()`.
**When to use:** WASM builds where `std::thread::spawn` is unavailable.
**Example:**
```rust
// In app.rs update() for WASM:
// Store pending MIDI messages in a Vec behind Rc<RefCell<>>
// Web MIDI callback pushes to this Vec
// Each frame, drain the Vec and process through harmony engine
fn update(&mut self, ctx: &egui::Context, _frame: &mut eframe::Frame) {
    // Process any pending MIDI messages
    let messages: Vec<Vec<u8>> = self.midi_queue.borrow_mut().drain(..).collect();
    for msg in messages {
        self.process_midi_message(&msg);
    }
    // ... render UI as before ...

    // Request continuous repaints when running (for polling)
    if self.state.is_running {
        ctx.request_repaint();
    }
}
```

### Pattern 3: eframe Web Entry Point
**What:** A `lib.rs` that exposes the app via `wasm_bindgen` for web builds.
**When to use:** WASM target only.
**Example:**
```rust
// src/lib.rs
#![cfg(target_arch = "wasm32")]

mod app;
mod chord;
mod harmony;
mod midi;
mod piano;
mod router;

use eframe::wasm_bindgen::{self, prelude::*};

#[wasm_bindgen]
pub struct WebHandle {
    runner: eframe::WebRunner,
}

#[wasm_bindgen]
impl WebHandle {
    #[wasm_bindgen(constructor)]
    pub fn new() -> Self {
        console_error_panic_hook::set_once();
        Self {
            runner: eframe::WebRunner::new(),
        }
    }

    #[wasm_bindgen]
    pub async fn start(&self, canvas_id: &str) -> Result<(), wasm_bindgen::JsValue> {
        let web_options = eframe::WebOptions::default();
        self.runner
            .start(
                canvas_id,
                web_options,
                Box::new(|cc| Ok(Box::new(app::ContrapunkApp::new(cc)))),
            )
            .await
    }
}
```

### Anti-Patterns to Avoid
- **Spawning threads in WASM:** `std::thread::spawn` panics on wasm32. Use frame-based polling or `wasm_bindgen_futures::spawn_local`.
- **Using `std::net` in WASM:** TCP sockets don't exist. Server/client mode must be disabled in WASM builds.
- **Blocking calls in WASM:** `recv_timeout`, `thread::sleep`, etc. block the single thread and freeze the browser. Use non-blocking patterns.
- **Using `println!` in WASM:** Goes nowhere. Use `web_sys::console::log_1` or the `log` crate with `console_log`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| WASM build pipeline | Custom wasm-bindgen scripts | Trunk | Handles wasm-bindgen, wasm-opt, asset hashing, HTML injection |
| Web MIDI API bindings | Manual JS FFI | web-sys with MIDI features | Already generated, type-safe bindings |
| JS Promise to Rust Future | Manual callback wiring | wasm-bindgen-futures | Standard bridge, handles edge cases |
| WASM panic debugging | Raw console errors | console_error_panic_hook | Provides Rust backtraces in browser console |
| Static file serving | Custom server | nginx Docker image | Correct MIME types, caching, compression |

**Key insight:** The Rust WASM ecosystem has mature tooling. The eframe_template repository provides a working reference for every web deployment concern.

## Common Pitfalls

### Pitfall 1: Thread Panic in WASM
**What goes wrong:** Code using `std::thread::spawn` compiles but panics at runtime on wasm32.
**Why it happens:** wasm32-unknown-unknown has no thread support.
**How to avoid:** Gate all `std::thread` usage with `#[cfg(not(target_arch = "wasm32"))]`. Move MIDI processing into the eframe update loop for WASM.
**Warning signs:** Runtime panic "cannot spawn threads" in browser console.

### Pitfall 2: Missing `getrandom` JS Feature
**What goes wrong:** Compilation fails with "getrandom: unsupported target" error.
**Why it happens:** The `rand` crate depends on `getrandom` which needs the `js` feature for WASM to use `crypto.getRandomValues()`.
**How to avoid:** Add `getrandom = { version = "0.2", features = ["js"] }` to wasm32 dependencies.
**Warning signs:** Build error mentioning getrandom.

### Pitfall 3: Web MIDI Requires HTTPS
**What goes wrong:** `navigator.requestMIDIAccess()` fails with permissions error.
**Why it happens:** Web MIDI API requires a secure context (HTTPS or localhost).
**How to avoid:** Fly.io provides HTTPS by default. For local dev, Trunk serves on localhost which is a secure context.
**Warning signs:** "SecurityError: requestMIDIAccess" in browser console.

### Pitfall 4: Web MIDI Browser Support
**What goes wrong:** MIDI doesn't work in Firefox/Safari.
**Why it happens:** Web MIDI API is only supported in Chromium-based browsers (Chrome, Edge, Opera).
**How to avoid:** Display a clear message when Web MIDI is unavailable. Check `navigator.requestMIDIAccess` existence before calling.
**Warning signs:** Feature detection fails silently.

### Pitfall 5: WASM File Size
**What goes wrong:** Initial page load is slow (multi-MB WASM file).
**Why it happens:** Rust WASM output can be large without optimization.
**How to avoid:** Already have `opt-level = "z"` and `lto = true` in release profile. Trunk runs `wasm-opt` automatically. Also enable gzip/brotli compression in nginx.
**Warning signs:** WASM file > 2MB after optimization.

### Pitfall 6: midir in WASM Uncertainty
**What goes wrong:** midir may not compile or work correctly for wasm32-unknown-unknown.
**Why it happens:** midir lists "Web MIDI" support but this may be for wasm-wasi or an older target. The wasm32-unknown-unknown target may not be fully tested.
**How to avoid:** Use web-sys directly for WASM MIDI instead of relying on midir. Gate midir usage behind `#[cfg(not(target_arch = "wasm32"))]`.
**Warning signs:** Compilation errors from midir on wasm32 target.

## Code Examples

### Web MIDI Access via web-sys
```rust
// Source: web-sys documentation + Web MIDI API spec
use wasm_bindgen::prelude::*;
use wasm_bindgen_futures::JsFuture;
use web_sys::{MidiAccess, MidiInput, MidiMessageEvent};

pub async fn request_midi_access() -> Result<MidiAccess, JsValue> {
    let window = web_sys::window().unwrap();
    let navigator = window.navigator();
    let promise = navigator.request_midi_access()?;
    let access = JsFuture::from(promise).await?;
    Ok(access.unchecked_into::<MidiAccess>())
}

pub fn list_midi_inputs(access: &MidiAccess) -> Vec<(String, MidiInput)> {
    let inputs = access.inputs();
    let mut result = Vec::new();
    // MidiInputMap is a JS Map, iterate with js_sys
    let entries = js_sys::try_iter(&inputs).unwrap().unwrap();
    for entry in entries {
        let entry = entry.unwrap();
        let arr: js_sys::Array = entry.into();
        let id: String = arr.get(0).as_string().unwrap();
        let input: MidiInput = arr.get(1).unchecked_into();
        result.push((id, input));
    }
    result
}
```

## Open Questions

1. **Does midir compile for wasm32-unknown-unknown?**
   - What we know: midir lists "Web MIDI" support and has wasm-bindgen deps
   - What's unclear: Whether it actually compiles and works on wasm32-unknown-unknown target with eframe
   - Recommendation: Gate midir behind `cfg(not(wasm32))` and use web-sys directly for WASM. Test midir WASM compilation as an optional improvement later.

2. **eframe 0.33 WebRunner API stability**
   - What we know: eframe has WASM support, eframe_template demonstrates it
   - What's unclear: Exact API for eframe 0.33 (template may use different version)
   - Recommendation: Check eframe 0.33 docs during implementation; the pattern is stable across versions.

3. **Web MIDI API `requestMIDIAccess` with sysex**
   - What we know: Basic MIDI access works without sysex permission
   - What's unclear: Whether Contrapunk needs sysex messages in browser
   - Recommendation: Start without sysex (`requestMIDIAccess()` with no options), add later if needed.
