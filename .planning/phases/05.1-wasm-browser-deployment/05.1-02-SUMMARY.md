# Phase 5.1 Plan 02: Web MIDI Integration Summary

Web MIDI frame-based polling replacing thread-based router for WASM builds.

## One-liner

Frame-based Web MIDI polling in eframe update() loop with HarmonyEngine processing and port-mapped output routing.

## What Was Done

### Task 1: Web MIDI backend (pre-completed in 05.1-01)
The `src/midi/web.rs` module was already implemented in Plan 05.1-01 with all required functions:
- `request_midi_access()` — async navigator.requestMIDIAccess()
- `list_midi_inputs()` / `list_midi_outputs()` — enumerate (id, name) pairs
- `connect_input()` — onmidimessage callback pushing to Rc<RefCell<Vec<Vec<u8>>>>
- `send_to_output()` — send bytes to MidiOutput by ID

No changes needed. Verified compilation passes.

### Task 2: Frame-based MIDI polling in app.rs
Added WASM-specific fields to `ContrapunkApp`:
- `midi_access: Rc<RefCell<Option<MidiAccess>>>` — shared async reference
- `midi_queue: Rc<RefCell<Vec<Vec<u8>>>>` — message queue from input callback
- `connected_output_ids: Vec<String>` — selected output device IDs
- `engine: HarmonyEngine` — owned directly (no thread needed)
- `wasm_input_notes` / `wasm_harmony_notes` — display state

Frame-based processing in `update()`:
1. Drain midi_queue each frame
2. Parse MIDI bytes (Note On/Off)
3. Process through HarmonyEngine (same harmonize_note_on/off as native)
4. Send to Web MIDI outputs via port map
5. Update input/harmony note sets for display
6. `ctx.request_repaint()` for continuous polling when running

## Decisions Made

1. **Task 1 already done**: web.rs was implemented as stubs in 05.1-01 but contained complete working code
2. **Engine ownership**: HarmonyEngine owned directly by ContrapunkApp in WASM (not behind Arc<Mutex>) since there are no threads
3. **Output routing**: Store output device IDs as strings, look up MidiOutput by ID each send (simple, correct)
4. **Device enumeration**: Populate available_inputs/outputs once MidiAccess arrives, refreshable via button
